# Phase 7 — Observe & Reward Loop — Full Detailed Spec

**Depends on:** Phase 6 (actions to observe outcomes for), Phase 5 (bandit to feed rewards back to)
**Unblocks:** Phase 8 (batch harness needs identical reward/audit logic), Phase 9 (audit trail writes originate here)
**Owner:** backend/integration owner (can be same as Phase 6)
**Estimated time:** ~1 day

---

## 1. Why this phase exists and why it matters more than it looks

Every phase before this one produces a decision and takes an action. None
of them, on their own, make the system *learn*. Phase 7 is the wire that
runs from "something happened in the real world" back to "the bandit's
beliefs update accordingly" — without it, Phase 5's contextual bandit is
just an elaborate random number generator that never actually gets smarter,
and your entire novelty claim ("the agent learns, not just acts") quietly
stops being true.

This phase also carries a second responsibility that's easy to
underweight: it's the **single source of truth for the audit trail**. Every
other phase produces data that only becomes meaningful once it's written to
`audit_log` in a consistent, complete way. If this phase has gaps — a
webhook that arrives but never gets processed, a reward that's computed
inconsistently between live mode and batch mode — your "explainable and
auditable" story develops holes exactly where a judge is most likely to
probe (ask to see a specific episode's full history, and if the chain is
broken, it's visible immediately).

Two properties matter more here than almost anywhere else in the system:

1. **Idempotency under at-least-once delivery.** This is not a hypothetical
   edge case — Razorpay, like virtually every modern webhook provider,
   explicitly documents that webhooks may be delivered more than once for
   the same event. Code that isn't idempotent here **will** double-count
   revenue recovered and **will** double-update the bandit, corrupting your
   headline metrics in a way that's easy to miss until a judge's demo
   triggers it live.
2. **Reward-logic parity between live mode and batch mode.** Phase 8's
   entire "controlled experiment" credibility depends on the batch harness
   using the *exact same* `RewardService` and `AuditLogService` as the live
   pipeline — if you write two different reward-computation implementations
   (one for "real" webhooks, one for "eval" simulation), you've quietly
   invalidated the comparison you're building your whole demo around.

## 2. Conceptual model — read this before touching code

### 2.1 Why webhook-driven, with polling as a fallback, not the reverse

There are three plausible designs for finding out "did the retried payment
succeed": (a) poll Razorpay's API repeatedly until you see a status change,
(b) rely entirely on Razorpay pushing a webhook to you, or (c) do both,
webhook-primary with polling as a safety net. Polling-only wastes API calls
and adds latency (you find out "late," on your polling cadence, not the
moment it happens). Webhook-only is architecturally correct but fragile in
practice — webhook delivery can fail silently due to your endpoint being
briefly down, a network issue, or a misconfigured endpoint URL, and you'd
have no way of knowing you missed something. The combination — webhook as
the primary, fast path, with a periodic reconciliation poll checking for
anything that should have resolved by now but hasn't — is the standard
production pattern for exactly this reason: it gets you speed *and*
correctness, and it's the pattern any senior payments engineer would
default to without being told.

### 2.2 Why reward computation is a separate service, not inline logic

It's tempting to compute the reward directly inside the webhook handler
(`if result == "recovered": reward = 1.0`, right there in the handler
function). Resist this. The reward function embodies your actual ML design
decision — the specific shaping described in `ML_DESIGN.md` §2.5 — and it
needs to be:
- Testable in complete isolation, without needing to construct a fake
  webhook payload just to test a one-line conditional.
- Reusable, verbatim, from Phase 8's batch harness (which never receives a
  real webhook at all — see §2.3).
- Changeable later (e.g., if you add time-decay shaping) without touching
  webhook-parsing code.

### 2.3 Why "live mode" and "batch mode" must share code, not just share intent

In live/demo mode, an outcome arrives via a real webhook (or a manual
"mark resolved" trigger for simulated nudges). In batch-evaluation mode
(Phase 8), there is no webhook at all — outcomes are generated by sampling
against the synthetic ground truth. These are **different sources of an
`Outcome` object**, but from the moment an `Outcome` exists, everything
downstream — reward computation, bandit update, audit write — must be
byte-for-byte identical logic. If Phase 8 reimplements its own version of
"compute reward from outcome" instead of importing `RewardService.compute`
directly, you've created two parallel reward implementations that can (and
eventually will) silently drift apart, and at that point your headline
"bandit beats baseline" number is being computed by different math on each
side, which is scientifically meaningless even if nobody notices during the
demo.

### 2.4 The `AuditLogService` as the single writer — why this really matters

`audit_log` is your evidence for "explainable, bounded, gated." If three
different code paths (webhook handler, reconciliation task, batch harness)
each independently constructed `AuditLog` rows with slightly different
field-population logic, you'd have no guarantee that every episode's
history is complete or consistent — some rows might have `cause_category`
populated and others not, purely due to which code path happened to write
them. Centralizing all writes through one service with one method signature
eliminates an entire class of "why does this audit row look different from
that one" bugs, and it's also just good software design: one clear owner
for one clear responsibility.

## 3. Detailed component design

### 3.1 `services/observe/reward_service.py`

```python
from dataclasses import dataclass

class RewardService:
    """The single source of truth for outcome -> reward mapping. Both the
    live webhook handler (this phase) and the batch evaluation harness
    (Phase 8) MUST call this exact class — never reimplement this logic
    elsewhere, even for 'just a quick eval script.'"""

    # Reward shaping per ML_DESIGN.md §2.5. Keep these as named constants,
    # not magic numbers scattered through call sites, so the ML design doc
    # and the code can never silently drift apart.
    REWARD_RECOVERED = 1.0
    REWARD_NOT_RECOVERED = 0.0
    REWARD_BLOCKED_BY_POLICY = -0.1

    def compute(self, outcome: "Outcome") -> float:
        if outcome.result == "recovered":
            return self.REWARD_RECOVERED
        if outcome.result == "blocked_by_policy":
            return self.REWARD_BLOCKED_BY_POLICY
        if outcome.result in ("not_recovered", "pending", "failed_permanently"):
            return self.REWARD_NOT_RECOVERED
        raise ValueError(f"unrecognized outcome.result: {outcome.result!r} — "
                          f"update RewardService.compute() to handle new outcome states explicitly, "
                          f"do not let unrecognized states silently default to 0.0")
```

**Note the explicit `raise` on an unrecognized `result` value** rather than
a silent default. This is a deliberate defensive choice: if someone later
adds a new `outcome.result` value elsewhere in the codebase (e.g.,
`"partially_recovered"`) without updating this function, you want a loud
failure during testing, not a silently-wrong reward flowing into the
bandit's learning.

### 3.2 `services/observe/webhook_handlers.py`

```python
import logging
from packages.db_models.models import Action, Outcome

logger = logging.getLogger(__name__)

def handle_payment_captured_webhook(payload: dict, db_session, bandit, reward_service, audit_log_service):
    razorpay_payment_id = payload["payment"]["id"]
    action = find_action_by_razorpay_ref(db_session, razorpay_payment_id)

    if action is None:
        # Don't crash — this can legitimately happen (test webhook, stale
        # reference, race with a not-yet-committed action row). Log loudly
        # for manual investigation, but let the handler return normally so
        # Razorpay doesn't interpret this as "please retry this webhook forever."
        logger.warning("webhook_unknown_razorpay_ref", extra={"razorpay_payment_id": razorpay_payment_id})
        return

    decision = action.decision
    outcome = Outcome(
        action_id=action.id,
        result="recovered",
        amount_recovered=payload["payment"]["amount"],
        time_to_resolution_hrs=hours_between(action.executed_at, now()),
    )
    outcome.reward = reward_service.compute(outcome)

    # Idempotent on redelivery: action_id has a unique constraint (see
    # DATABASE_DESIGN.md — add this constraint in Phase 1 if not already
    # present), and this upsert is a no-op on the second identical delivery.
    upserted = upsert_outcome(db_session, outcome, conflict_target="action_id")

    if upserted.is_new:
        # Only feed the bandit and re-write audit on the FIRST delivery —
        # a redelivered webhook must not double-update learning state.
        bandit.update(context_bucket_for(decision.event, decision.diagnosis), decision.chosen_arm, outcome.reward)
        audit_log_service.write(event=decision.event, decision=decision, outcome=outcome)
    else:
        logger.info("webhook_redelivery_deduped", extra={"action_id": str(action.id)})


def handle_subscription_charge_failed_webhook(payload: dict, db_session, ...):
    """Mirror structure to handle_payment_captured_webhook, for the
    complementary failure-confirmation event — e.g., a scheduled retry that
    Razorpay processed and confirmed as still failed. Implement using the
    same idempotent-upsert + is_new-gated side-effect pattern."""
    ...
```

**The `upserted.is_new` gate is the critical idempotency mechanism** — the
upsert itself prevents a duplicate *row*, but you must also prevent
duplicate *side effects* (bandit update, audit write) on redelivery, which
requires knowing whether this specific call actually inserted a new row or
just no-op'd against an existing one. Don't skip this distinction; a
naive "upsert then always update the bandit" implementation will silently
double-count every redelivered webhook.

### 3.3 `services/audit/audit_log_service.py`

```python
class AuditLogService:
    """The ONLY code path permitted to write to the audit_log table.
    Called from: services/observe (this phase), the reconciliation task,
    and eval/run_batch.py (Phase 8) — never from apps/api route handlers
    directly, never from services/act."""

    def __init__(self, db_session):
        self.db_session = db_session

    def write(self, event, decision=None, gate_result=None, outcome=None):
        self.db_session.add(AuditLog(
            event_id=event.id,
            episode_id=event.episode_id,
            cause_category=event.diagnosis.cause_category if getattr(event, "diagnosis", None) else None,
            chosen_arm=decision.chosen_arm if decision else None,
            gate_result=gate_result.passed if gate_result else None,
            simulated=(decision.action.simulated if decision and getattr(decision, "action", None) else None),
            outcome_result=outcome.result if outcome else None,
            reward=outcome.reward if outcome else None,
        ))
        self.db_session.commit()

    def write_error(self, decision, code: str, reason: str):
        """Called by services/act on a permanent/exhausted-retry failure
        (see PHASE_06_act_DETAILED.md section 3.4) — a distinct method so
        error-path audit entries are structurally tagged, not conflated
        with normal outcome rows."""
        self.db_session.add(AuditLog(
            event_id=decision.event.id,
            episode_id=decision.event.episode_id,
            chosen_arm=decision.chosen_arm,
            outcome_result="failed",
            reward=None,
        ))
        # Consider a separate error_code column on audit_log if not already
        # present in DATABASE_DESIGN.md — flag this to the team if so, rather

        ...
```

### 3.4 `apps/worker/src/tasks/reconcile_payment_status.py`

```python
from datetime import timedelta

RECONCILIATION_THRESHOLD = timedelta(hours=6)  # how "stale" an unresolved action must be to poll for it

@celery_app.task
def reconcile_payment_status():
    stale_actions = find_actions_without_outcome(
        statuses=["scheduled", "executed"],
        older_than=now() - RECONCILIATION_THRESHOLD,
        simulated=False,  # only real Razorpay actions have anything to poll for
    )
    reconciled_count = 0
    for action in stale_actions:
        if action.razorpay_ref_id is None:
            continue  # scheduled-but-not-yet-executed delayed actions have no ref yet — nothing to poll
        status = razorpay_client.get_payment_status(action.razorpay_ref_id)
        if status["status"] == "captured":
            # Route through the SAME handler as a real webhook would, so
            # reconciliation and webhook-driven paths produce IDENTICAL
            # outcome/audit records — do not write a parallel "reconciled"
            # outcome path with different logic.
            handle_payment_captured_webhook(
                payload={"payment": {"id": action.razorpay_ref_id, "amount": status["amount"]}},
                db_session=db_session, bandit=bandit, reward_service=reward_service,
                audit_log_service=audit_log_service,
            )
            reconciled_count += 1
    logger.info("reconciliation_run_complete", extra={"reconciled_count": reconciled_count, "checked": len(stale_actions)})
    return reconciled_count
```

**This task reuses `handle_payment_captured_webhook` directly** rather than
duplicating its logic — this is the concrete implementation of the
"webhook + reconciliation, same downstream code" principle from §2.1. It
also means the idempotency guarantee from §3.2 covers the reconciliation
path for free: if a webhook arrives *after* reconciliation already caught
it, the upsert-and-`is_new`-gate logic prevents any double-processing.

```python
@router.post("/v1/events/{event_id}/mark-resolved")
def mark_resolved(event_id: str, body: MarkResolvedRequest, db_session=Depends(get_db)):
```

## 4. Full edge-case matrix (expanded)

| # | Case | Expected behavior | How to test |
|---|---|---|---|
| 1 | Webhook arrives for an action already reconciled by the polling job | Idempotent upsert on `action_id`, `is_new=False`, no duplicate bandit update or audit write | Integration test: run reconciliation first, then deliver the webhook, assert exactly one `outcome` row and one bandit update |
| 2 | Webhook references an unknown `razorpay_ref_id` | Logged as a warning, handler returns normally (does not raise, so Razorpay doesn't retry-storm an endpoint that will never resolve it) | Unit test: payload with a ref not present in `actions`, assert no exception, assert a warning log occurred |
| 3 | Same webhook delivered twice (identical payload, back to back) | Only one `outcome` row exists; only one bandit update occurred | Test in §5.2 |
| 4 | Simulated nudge action | No real webhook will ever arrive for it — must be resolved via the manual trigger (live demo) or Phase 8's simulator (batch), never left permanently unresolved without explanation | Verify `find_actions_without_outcome` excludes `simulated=True` actions from reconciliation polling (they'd never resolve via Razorpay polling regardless) |
| 5 | `bandit.update()` called with a `context_bucket` for a taxonomy that's since changed (e.g., a new cause category added, buckets renumbered) | Falls back to the bandit's own default-prior handling (Phase 5's `RedisArmStatsStore.get_stats` already handles unseen buckets) — this phase should NOT add a second, redundant fallback layer here; trust Phase 5's contract | Integration test using a deliberately novel context_bucket string, assert no exception propagates from the bandit call |
| 6 | Reconciliation runs while a webhook for the same action is mid-flight (race) | The idempotent upsert + `is_new` gate resolves this correctly regardless of which one "wins" the race — verify with a concurrency test, not just a sequential one | Concurrency test: fire both paths concurrently against the same action, assert exactly one outcome row and one bandit update afterward |
| 7 | `RewardService.compute()` receives an `outcome.result` value not in the known set | Raises `ValueError` loudly, does not silently return 0.0 | Unit test asserting the raise |
| 8 | Manual "mark resolved" called twice for the same event (accidental double-click during a demo) | Should behave with the same idempotency guarantee as a webhook — route through the same upsert-and-gate pattern, don't treat this as a "trusted internal" path that skips idempotency | Unit test: call the endpoint twice, assert only one outcome/bandit-update occurred |

## 6. Observability — what to log at runtime

Every webhook handler invocation should log: `razorpay_payment_id`,
`action_id` (once resolved), whether it was a fresh delivery or a
deduplicated redelivery, and the computed reward. The reconciliation task
should log a summary every run: how many stale actions were checked, how
many were reconciled, and how many are still genuinely pending (not yet
resolved even after polling — this number, if it grows, is an early warning
sign worth watching during your own testing, not just in production).
