# PRD — AI Revenue Recovery Agent

**Status:** Draft v1
**Owner:** [team lead name]
**Track:** Razorpay Buildathon 2026, Track 03 — AI Revenue Recovery

---

## 1. Problem Statement

Merchants lose revenue not through one clean failure but through a chain of
small breakages: a card payment is declined, a subscription mandate fails to
renew, a customer abandons checkout mid-flow, or a B2B invoice goes overdue.
Each of these events, left alone, is quietly-compounding lost revenue — most
merchants have no systematic way to detect these moments, diagnose *why* they
happened, and act on them before the customer disengages entirely.

Today this is handled, if at all, by:
- Fixed-schedule retry logic with no awareness of *why* a payment failed.
- Manual follow-up by support/collections staff, which doesn't scale.
- No feedback loop — the same ineffective retry strategy is used regardless
  of whether it's ever worked before.

**Core insight:** revenue recovery is not one decision, it's a *sequence* —
detect → diagnose → decide → act → observe → stop — and the "decide" step is
almost always hardcoded today. It should learn.

## 2. Goal

Build an agent that closes the loop from "a payment just failed" to "money is
recovered or the case is honestly logged as unrecoverable," and prove it
works with **measured, baseline-compared results on a real batch**, not a
single cherry-picked example.

## 3. Target user (merchant persona)

A mid-size D2C or SaaS merchant on Razorpay processing subscription and
one-time payments, who is currently losing an estimated 8–15% of billable
revenue to failed payments and mandate lapses, and has no automated recovery
system beyond a single generic retry.

## 4. Scope

### In scope (v1 — hackathon build)
- Failed payment / failed subscription mandate detection (via synthetic
  event stream that mimics Razorpay webhook payloads).
- Root-cause diagnosis of the failure (insufficient funds, expired card,
  OTP failure, bank timeout, mandate inactive, hard decline, etc.).
- A learning decision policy (contextual bandit) that selects the recovery
  intervention and its timing.
- Execution of the intervention:
  - Real: retry attempt / payment link creation via Razorpay **test-mode** API.
  - Simulated (clearly labeled): outbound nudge message (SMS/WhatsApp-style,
    Hinglish or English) generated by an LLM.
- Stopping-rule / compliance engine: max retry attempts, cool-off windows,
  hard-stop on explicit customer decline/opt-out.
- Promise-to-pay tracking for B2B-style overdue cases.
- Full audit trail: every event → diagnosis → decision → action → outcome.
- Batch evaluation: run 150–300 synthetic events through the agent and a
  naive baseline, report recovery rate and ₹ recovered for both.
- Dashboard: live event flow, audit trail table, metrics panel, bandit
  learning curve, exception list.

### Out of scope (explicitly, for v1)
- Real customer communication (no real SMS/WhatsApp sends) — simulated only.
- Real card data / PCI-scope handling — synthetic data only, never real PII.
- Multi-merchant / multi-tenant support — single demo merchant is enough.
- Full B2B receivables ledger integration — a simplified promise-to-pay
  tracker stands in for it.
- Any *offense-capable* logic (this track is recovery, not risk scoring —
  keep clear of anything that could be read as adversarial/exploitative).

## 5. Success metrics

| Metric | Definition | Target for demo |
|---|---|---|
| Recovery rate | % of failed events where money was ultimately recovered | Meaningfully higher than baseline (report both, don't fabricate a number) |
| ₹ recovered (batch) | Total amount recovered across the batch | Report absolute + % of at-risk revenue |
| Lift vs. baseline | Recovery rate (agent) − Recovery rate (naive same-day retry) | This is the single most important number in the demo |
| Time-to-recovery | Average time from failure to recovered payment | Report distribution, not just mean |
| Stopping-rule compliance | 100% of events respect max-attempts / cool-off / opt-out rules | Must be 100% — this is a correctness bar, not an optimization target |
| Exception rate | % of events the agent explicitly could not resolve | Report honestly; a 0% exception rate is a red flag, not a win |
| Bandit convergence | Recovery rate improving over the course of the batch run | Visualized as a learning curve |

## 6. User stories

- *As a merchant*, I want failed subscription payments to be automatically
  retried at the right time with the right message, so I stop manually
  chasing customers.
- *As a merchant*, I want to see exactly why the agent chose an action, so I
  trust it enough to let it run unsupervised.
- *As a customer*, I want the agent to stop contacting me after I've said no,
  so recovery doesn't feel like harassment.
- *As a judge/recruiter*, I want to see honest, reproducible numbers with a
  clear baseline, so I can trust the claimed impact.

## 7. Constraints & principles

1. **Explainable** — every decision has a human-readable reason attached at
   the time it's made, not reconstructed after the fact.
2. **Bounded** — every action type has a hard ceiling (max attempts, max
   spend on communication, max escalation level).
3. **Gated** — nothing executes without passing the stopping-rule engine
   first; opt-outs and hard declines are terminal states.
4. **Honest measurement** — baseline comparison is mandatory; exceptions are
   reported, not hidden.
5. **Test-mode only** — no production financial systems are touched.

## 8. Risks

| Risk | Mitigation |
|---|---|
| Synthetic data looks unrealistic / judges suspect it's rigged | Introduce genuine noise, a realistic failure-cause distribution, and some genuinely unrecoverable cases |
| Bandit doesn't visibly converge within a small batch | Pick a bandit algorithm with fast convergence (Thompson Sampling); tune batch size and reward variance during testing, not on demo day |
| Live demo API call fails on stage | Have a pre-recorded fallback run's data cached; state clearly which parts are live vs. cached |
| Scope creep (trying to build all 7 example directions) | Lock to ONE end-to-end loop (subscription/mandate recovery) as the spine; treat Hinglish nudges + promise-to-pay as thin add-ons on top of the same spine, not separate systems |
